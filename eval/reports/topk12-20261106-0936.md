### ta-01 run 1: When is a discount code generated for a client, and what does the code look like?

Answer: A discount code is generated for a client during `BookingService.recordMilesReward` when the client books a flight that is their 3rd flight (or a multiple of 3) in the current calendar year. Specifically, it counts the flights for the client in `currentYear` (`LocalDate.now().getYear()`) using `milesRewardRepository.countFlightsByClientAndYear(client, currentYear)`, and generates the code if `(flightsThisYear + 1) % 3 == 0` (every 3 flights per calendar year).

The code is generated by `BookingService.generateDiscountCode()`, which returns string `"DISC-"` concatenated with the first 8 uppercase characters of a random UUID (`UUID.randomUUID().toString().substring(0, 8).toUpperCase()`), for example: `DISC-EDDB7CDE`.

- [x] on every third flight of the client in the current year
- [x] the code is DISC- followed by 8 random uppercase characters taken from a UUID

### gh-01 run 1: How is the user-service organised into layers?

Answer: The user-service is organized into three main layers across its `app/` modules:

1. **Interface layer / HTTP layer (`app/routes.py`)**:
   - Maps HTTP verbs and paths to service function calls using a FastAPI router.
   - It is the only layer that knows about HTTP.
   - Routes only call service functions and never call repository functions directly. They catch `ValueError` from the service layer and raise `HTTPException` instead.

2. **Application layer / Business logic (`app/service.py`)**:
   - Contains business logic and decision-making (e.g., password hashing, raising errors when a user is not found, and converting ORM objects into Pydantic schemas).
   - Only calls repository functions and never queries the database directly.
   - Returns Pydantic schemas (`UserOut`, `UserList`) and raises `ValueError` for business errors.

3. **Infrastructure layer / Database queries (`app/repository.py`)**:
   - Handles raw database queries using a SQLAlchemy `Session` and returns ORM objects.
   - It is the only layer allowed to write SQL / ORM queries.
   - Has no HTTP knowledge and no business rules.

Supporting files in the `app/` folder include:
- `app/main.py`: FastAPI application initialization that mounts the router.
- `app/database.py`: Database engine and session factory.
- `app/models.py`: SQLAlchemy ORM model (`User`).
- `app/schemas.py`: Pydantic DTOs (`UserCreate`, `UserOut`).

- [x] routes handle HTTP, the service layer holds the business logic, the repository does the database queries

### cr-02 run 1: Why is missing-value imputation not done in the data cleaning notebook?

Answer: Missing-value imputation is not done in the data cleaning notebook (01_data_cleaning.ipynb) because fitting preprocessing parameters from the data—such as a median or mean—before the train/test split causes data leakage by leaking information from the test set into training. This leakage causes validation metrics to look better than actual production performance. Instead, notebook 01 leaves NaN values intact so that notebook 03 can perform the time-aware train/test split first and fit the imputer on the training set only. Additionally, keeping imputation in notebook 03 after the split helps enforce the rule to fit preprocessing on train only and makes it harder to accidentally do imputation before the split.

- [x] the imputer (median, mean, scaler) must be fit on the training split only
- [x] fitting it before the split leaks test information into training

### fs-04 run 1: How does the scanner decide where a streamer is located, and how reliable is that?

Answer: The scanner infers a streamer's location using the function `guess_region(text, start_hours)` in `streamer_finder_v3.py`, following the hierarchy where profile words beat timezone, which beats start hours:

1. **Target Profile Words and Flags (High Confidence):** Checks profile text for matching target words (`TARGET_WORDS` for UK, US, CA) or country flag emojis (`FLAGS` for UK, US, CA). If checking UK and "british columbia" appears in the lowercased text, "british" is discarded. The region with the maximum pattern hits is selected and returned with "high" confidence.
2. **Outside Target Market Words (High Confidence):** Checks text against `EXCLUDE_PATTERN` (`EXCLUDE_WORDS`). If any outside market words match, it returns region `"other"` with "high" confidence.
3. **Timezone Words (Medium Confidence):** Checks text against `TZ_PATTERNS` (`TIMEZONE_WORDS`). If matched, it returns the corresponding region with "medium" confidence.
4. **Start Hours (Low Confidence):** Analyzes the proportion of stream start hours across three time windows:
   - Asia-Pacific (`apac`): hours 7 through 13 (`7 <= h <= 13`). If `apac >= 0.7`, returns region `"other"` with "low" confidence.
   - UK (`uk`): hours 16 through 22 (`16 <= h <= 22`). If `uk >= 0.7`, returns region `"UK?"` with "low" confidence.
   - North America (`na`): hours 23 and above or 6 and below (`h >= 23 or h <= 6`). If `na >= 0.7`, returns region `"US/CA?"` with "low" confidence.
5. **No Match:** Returns region `"unknown"` with `"none"` confidence.

**Reliability:**
- Because Twitch publishes no country data, location is strictly inferred and explicitly labelled with its confidence level ("high", "medium", "low", or "none").
- Hours-only guesses are marked as low confidence because location inference cannot distinguish a UK streamer from a European streamer broadcasting in English at the same hour.

- [x] location is inferred because Twitch publishes no country
- [x] profile text gives high confidence, timezone mentions medium, streaming hours alone only a low-confidence guess
