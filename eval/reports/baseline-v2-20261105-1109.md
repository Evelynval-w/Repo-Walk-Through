### ta-01 run 1: When is a discount code generated for a client, and what does the code look like?

Answer: A discount code is generated for a client during `BookingService.recordMilesReward` when `(flightsThisYear + 1) % 3 == 0`, where `flightsThisYear` is determined by `milesRewardRepository.countFlightsByClientAndYear(client, currentYear)` for the current year (`LocalDate.now().getYear()`) (i.e., on the 3rd flight or a multiple of 3 flights in the same year).

- [x] on every third flight of the client in the current year
- [x] the code is DISC- followed by 8 random uppercase characters taken from a UUID

### gh-01 run 1: How is the user-service organised into layers?

Answer: The user-service is organized into the following layers:

1. **Interface Layer / HTTP Layer (`app/routes.py`)**: Handles HTTP endpoints and FastAPI router definitions, mapping HTTP verbs and paths to service function calls. It is the only layer that knows about HTTP. Routes must never call repository functions directly and must always go through the service layer.
2. **Application Layer / Business Logic (`app/service.py`)**: Contains business logic and decisions (such as password hashing, raising errors when a user is not found, and converting ORM objects into Pydantic schemas). It only calls repository functions and never queries the database directly.
3. **Repository Layer (`app/repository.py`)**: Handles raw database queries with no business logic.

Supporting components include:
- **`app/models.py`**: Contains SQLAlchemy ORM models (`User`).
- **`app/schemas.py`**: Contains Pydantic DTOs (`UserCreate`, `UserOut`).
- **`app/database.py`**: Manages the engine and session factory.
- **`app/main.py`**: Initializes the FastAPI app and mounts the router.

- [x] routes handle HTTP, the service layer holds the business logic, the repository does the database queries

### cr-02 run 1: Why is missing-value imputation not done in the data cleaning notebook?

Answer: Missing-value imputation is not done in the data cleaning notebook (notebook 01) because any preprocessing step that fits parameters from data—such as a median or mean—must be fit on the training set after the train/test split. Imputing before the split causes information from the test set to leak into training through those parameters (data leakage), making validation metrics appear better than production performance. To respect the "fit preprocessing on train only" rule, imputation was moved to `03_feature_engineering.ipynb` where the time-aware train/test split occurs first, allowing the imputer to be fit on the training set only while keeping NaN values intact in notebook 01.

- [x] the imputer (median, mean, scaler) must be fit on the training split only
- [x] fitting it before the split leaks test information into training

### fs-04 run 1: How does the scanner decide where a streamer is located, and how reliable is that?

Answer: The scanner infers location using the `guess_region(text, start_hours)` function in `streamer_finder_v3.py`. It prioritizes signals in the order: profile words beat timezone beat start hours.

### How it decides location:
1. **High Confidence (Target Profile Words & Exclusions):**
   - Checks text for target words/flags (`TARGET_PATTERNS`, `FLAGS` for UK, US, CA). If the region is UK and "british columbia" appears in the text, "british" is discarded. It selects the region with the most word hits, returning confidence `high`.
   - Checks for non-target market words (`EXCLUDE_PATTERN`). If found, it returns region `other` with confidence `high`.
2. **Medium Confidence (Timezones):**
   - Checks profile text for timezone patterns (`TZ_PATTERNS` like GMT, BST, EST, PST, etc.). If matched, returns the region with confidence `medium`.
3. **Low Confidence (Go-live Hours):**
   - Calculates the proportion of start hours:
     - Asia-Pacific hours (`7 <= h <= 13`): If proportion `>= 0.7`, returns `other`, confidence `low`.
     - UK evening hours (`16 <= h <= 22`): If proportion `>= 0.7`, returns `UK?`, confidence `low`.
     - North American evening hours (`h >= 23 or h <= 6`): If proportion `>= 0.7`, returns `US/CA?`, confidence `low`.
4. **Fallback:**
   - If no conditions match, returns `unknown` with confidence `none`.

### Reliability:
- **Confidence Labels:** Because Twitch does not publish country data, location is inferred and labeled with explicit confidence levels (`high`, `medium`, `low`, or `none`). Profile text and timezone mentions are treated as `high` and `medium` confidence, while hours alone are marked as a `low` confidence guess.
- **Known Limitation:** Location inference cannot distinguish a UK streamer from a European one streaming in English at the same hour, which is why hours-only guesses are separately labelled (e.g., `UK?`).

- [x] location is inferred because Twitch publishes no country
- [x] profile text gives high confidence, timezone mentions medium, streaming hours alone only a low-confidence guess
